# Changelog

## 0.1.6

- **Owner-authorized actions** (OWNER-ACTIONS-1): действия проектного
  реестра с полем `owner_auth` исполняются только при активной
  authorization владельца. Машинное состояние — `bin/owner_auth.py`
  (create/check/consume/list; `authorizations/AUTH-*.json`): привязка к
  project+action+SHA(40hex), одноразовость (consume после успешного
  исполнения), идемпотентный create, `--requires-prior-action` для цепочек
  (production_go требует executed owner_accept того же SHA; OWNER PASS не
  даёт production автоматически). Без authorization точная форма действия —
  FATAL DENY с точной причиной; после успеха — consume и audit
  (PROJECT_ACTION_ALLOWED/PROJECT_ACTION_EXECUTED).
- Read-форма `git worktree list [--porcelain]` разрешена (инертная замена
  в матче); write-формы worktree (add/remove/prune/move/lock/unlock) —
  по-прежнему SECURITY FATAL (jail-escape). Причина: реальный прогон
  выпуска погиб на ложном deny `git worktree list` при read-only проверке
  состояния.
- Самопроверка: секция 16 (23 проверки) — worktree read/write, owner-действия
  без/с чужой/с неверной authorization, consume+повтор, already-applied
  идемпотентность, production_go без prior и с prior, прямые
  merge/push/deploy-prod/guard-root — FATAL, сквозной run_task с consume.
  Итог: default 212/0, full 376/0.

## 0.1.5

- Таксономия DENY (SAFE-RETRY-1): security-причины по-прежнему FATAL
  (PERMISSION_VIOLATION, без изменений); DENY только по форме команды —
  составная команда с не-allowlisted git-глаголом или одиночный неизвестный
  git-глагол — при доказанной security-чистоте каждой части (каждая часть
  прогоняется через полный guard без form-правила) становится recoverable:
  исходная команда НЕ исполняется, модель получает системную заметку
  «выполни операции отдельными разрешёнными командами», лимит попыток
  (по умолчанию 2, env ORCH_TEST_SHAPE_DENY_MAX), после исчерпания —
  PERMISSION_VIOLATION с evidence. Событие GUARD_RECOVERABLE_DENIED —
  внутренний audit; отчёт владельцу не краснеет, если прогон исправился.
  Мотивация: реальный прогон погиб на первом же ходе из-за разведочной
  цепочки с git cat-file, хотя ничего не было исполнено.
- Поведение разрешённых команд не изменилось: составные команды, целиком
  проходящие guard, остаются разрешёнными (продовые паттерны
  `sed | head`, `cd X && cat`, `git add && git commit`; все прежние
  allow-тесты зелёные). Части recoverable-команд никогда не исполняются
  автоматическим парсингом.
- Промпт исполнителя: ровно одна shell-команда на вызов, без цепочек
  ';', '&&', '||'; при recoverable-deny — повторить отдельными
  разрешёнными командами, DENY не обходить.
- Самопроверка: секция 15 (14 проверок) — recoverable 126 без исполнения,
  одиночный form-deny, части по отдельности ALLOW, шесть security-случаев
  остаются FATAL 125 (guard root, push, deploy-prod, curl|sh,
  `; rm -rf`, `; cat secret.env`), сценарий инцидента жив, лимит попыток,
  отчёт владельцу без красного. Итог: default 212/0, full 353/0.

## 0.1.4

- Project actions доведены до исполнителя: registered actions публикуются в
  контексте задачи (точная форма: env по имени+формату, argv без добавок) с
  пояснением, что FORBIDDEN-пути означают запрет ИЗМЕНЯТЬ файлы, а исполнение
  зарегистрированного действия — предусмотренное исключение; системный промпт
  исполнителя больше не утверждает безусловный запрет deploy-скриптов.
  Причина: детерминированный guard уже пропускал точную форму, но модель
  отказывалась её выполнять, доверяя промпту (реальный случай staging deploy).
- Самопроверка: контекст задачи с действиями содержит секцию PROJECT ACTIONS;
  задачи без действий секции не получают; инвариант текста системного промпта.
  Итог: default 212/0, full 339/0.

## 0.1.3

- Добавлен универсальный механизм **project_actions** — точные
  проектно-ограниченные разрешения в реестре проекта (`config/projects.json`).
  Действие (например, штатный staging deploy) допускается ТОЛЬКО при
  точном совпадении команды: env-присваивания строго по `env_from_model`
  (имя + pattern, напр. `STAGING_SHA` = ровно 40 hex), `argv` токен-в-токен
  без опций/shell-связок/редиректов, скрипт — обычный файл внутри
  task-worktree (не симлинк), только writable-режим, guard_roots не
  встречаются в токенах. Фиксированные env (`env_fixed`) добавляет
  оркестратор при исполнении — секреты/канонические пути не проходят через
  команду модели; разрешение фиксируется в audit trail
  (`PROJECT_ACTION_ALLOWED`). Проекты без `project_actions` и все прочие
  команды (включая любые production deploy) проходят прежнюю цепочку
  запретов без изменений.
- Мотивация: реальная задача ночного прогона требовала
  `STAGING_SHA=<sha> bash ops/deploy-staging.sh` и корректно
  блокировалась общим запретом deploy; теперь это действие описывается в
  реестре проекта как конфигурация универсального механизма (ядро
  не привязано к имени проекта).
- Самопроверка: секция 14 (22 проверки) — ALLOW точной формы и исполнение
  с env_fixed, DENY для production-вариантов, произвольных скриптов,
  добавочных argv/env, короткого/длинного/не-hex SHA, shell-обходов,
  чужого env-имени, проекта без действий, чужого worktree,
  symlink-подмены; сквозной сценарий run_task с audit-событием.
  Итог: default 212/0, full 336/0.

## 0.1.2

- Исправлена логика no-write deadline: в арифметическом выражении bash
  использовалось `-eq` (`(( writes -eq 0 ))` — синтаксическая ошибка,
  условие всегда ложно); теперь корректное `writes == 0`. До фикса ветка
  «нет записи за первые `first_write_target_minutes` минут → эскалация
  `no_write_in_*min` на takeover-модель» была мертва (в стартовых профилях
  её частично дублировал stall-дедлайн с тем же порогом минут, поэтому
  дефект не был заметен). Для детерминированной проверки добавлен
  тест-шов `ORCH_TEST_FIRST_WRITE_MIN` и сценарий самопроверки,
  проходящий через эту ветку (эскалация → takeover → RESULT).
- Устранён лишний review для terminal RESULT: присваивание статуса
  попытки использовало `local` на верхнем уровне скрипта (вне функции —
  ошибка bash; присваивание после него всё же выполнялось, но с
  stderr-шумом и утечкой в глобальную область). Теперь обычное
  присваивание; самопроверка фиксирует контракт: терминальный
  NO_CHANGE_REQUIRED/NEEDS_OWNER_INPUT/BLOCKED на любом risk принимает
  напрямую (REVIEW_SKIPPED, ноль review-вызовов, без ошибок области
  видимости).
- Исправлен Intake launch после переименования `ag_task.sh` → `task.sh`:
  intake.py вызывал старое имя, и настоящий запуск (без `--dry-run`)
  падал «Не удалось создать run» на любой установке продукта. Добавлен
  сквозной тест: Intake → READY_TO_RUN → launch без --dry-run → run
  создан → night_run доводит задачу до RESULT (мок-модель, без сети).
  Совместимый алиас `bin/ag_task.sh` в продукт НЕ добавлен: это имя не
  существовало ни в одном публичном релизе, а его наличие ослабляло бы
  регрессионный тест.
- `task.sh` теперь корректно определяет корень установки: script-relative
  по расположению самого скрипта (versioned installs вида
  `.../night-orchestrator-v0.1.2` работают без переменных окружения);
  явный `ORCH_ROOT` по-прежнему имеет приоритет. До фикса молчаливый
  дефолт `$HOME/.local/share/night-orchestrator` ломал task.sh на
  установках по другим путям.
- Добавлены сквозные проверки самопроверки: no-write deadline
  срабатывает; terminal RESULT не проходит лишний review; Intake launch
  создаёт настоящий run; task.sh работает из versioned install и из
  случайного temp-path; явный ORCH_ROOT переопределяет auto-root
  (5b-8/9/10, 7g, 7h, 11M; default 212, full 314 проверок).

## 0.1.0 — первый внешний предварительный выпуск

- Безопасное автономное исполнение задач в одноразовом Git worktree;
  основной чекаут и production по умолчанию недоступны моделям.
- Машинные контракты TASK / RESULT / INTAKE (JSON-схемы), структурный
  финальный результат каждого прогона, отчёты владельцу человеческим
  языком (всегда, идемпотентно).
- Детерминированные ограничения команд и путей (shell-код, не промпты):
  запрет push/merge/deploy, docker/systemctl, сети, секретов, запретных
  корней проекта; различение read/write-команд Git; корректная работа с
  регулярными выражениями в awk/sed.
- Роли моделей (исследователь / исполнитель / сильный финализатор /
  рецензент) с конфигурируемыми провайдерами и резервными моделями;
  усиление модели по событию (stall, исчерпание лимита рассуждения).
- Бюджеты исполнения: turns и время, лимит чтения до первой записи,
  дополнительный бюджет после записи, резерв на финализацию RESULT.
- Intake-модуль: приём сообщений обычным языком (обсуждение / бэклог /
  задача), цикл уточняющих вопросов 1–3, связывание ответов владельца.
- Примеры интеграции с OpenClaw (проектный навык-обёртка).
- Границы владельца: OWNER PASS (принятие кода) и OWNER GO (production);
  автоматического обхода нет.
- Самопроверка: ~300 сценариев без секретов, внешних моделей и production.

Историю отладки до выделения продукта см. в git-истории проекта.
