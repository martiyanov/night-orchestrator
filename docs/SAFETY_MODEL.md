# Модель безопасности

Принцип: **безопасность обеспечивается кодом, а не промптами.** Модель может
ошибаться или быть уговорена; гейти — нет.

## Контуры

1. **Worktree-изоляция**: каждая writable-задача — отдельный git worktree
   (`worktree_root` проекта); основной чекаут не трогается.
2. **allowed_paths / forbidden_paths** (реестр проекта): изменения только в
   разрешённых путях; проверяется по фактическому диффу.
3. **guard_roots** проекта: целые корни (например, production-каталог),
   недоступные из команд вообще — и на чтение, и на запись.
4. **Запреты по классам команд** (обоих режимов): push/merge/reset/rebase/
   clean, deploy-скрипты, docker/systemctl, сеть (curl/ssh/…), установка
   пакетов, `sudo`, вложенные shell/eval, `.env*`, секреты, `data/`,
   инъекции PATH/GIT_DIR/hooks, `rm -rf`.
5. **project_actions** (реестр проекта, 0.1.3): точечные разрешения для
   ИСКЛЮЧИТЕЛЬНО точной формы команды (напр. штатный staging deploy:
   `STAGING_SHA=<40hex> bash ops/deploy-staging.sh`) — только writable,
   только для проекта с описанным действием, скрипт обычным файлом внутри
   worktree, без опций/shell-связок/лишних env; фиксированные env приходят
   из реестра, не от модели; фиксируется в audit (`PROJECT_ACTION_ALLOWED`).
   Это НЕ ослабление контура 4: все остальные команды (включая production
   deploy) проходят прежние запреты.
5a. **Таксономия DENY** (0.1.5): security-причины (production/guard roots,
   deploy без проектного действия, секреты, запрещённые записи, инъекции,
   обход guard) — по-прежнему немедленный PERMISSION_VIOLATION (FATAL).
   DENY только по ФОРМЕ команды (составные команды с не-allowlisted
   git-глаголом, одиночный неизвестный git-глагол) при доказанной
   security-чистоте каждой части (полный guard без form-правила) —
   recoverable: команда НЕ исполняется, модель получает инструкцию
   выполнить операции отдельными разрешёнными командами (лимит попыток,
   по умолчанию 2), владелец красного сообщения не получает. Составные
   команды, целиком проходящие guard, разрешены как раньше (проверенные
   продовые паттерны `sed | head`, `cd X && cat`, `git add && git commit`).
5b. **Owner-authorized actions** (0.1.6): повтор успешно исполненного
   owner-действия (action+sha) в ТОМ ЖЕ run — no-op ALREADY_EXECUTED
   (0.1.7): не исполняется повторно, не нарушение, владелец красного не
   получает; источник истины — structured run-state фактов исполнения.
   Другой run/sha/action или неудавшаяся попытка — прежняя security-семантика. merge/push/release выполняются
   только как project_actions с полем owner_auth — при активной
   одноразовой authorization владельца (project+action+SHA), отдельной
   для production (production_go требует executed owner_accept того же
   SHA). Свободный executor shell для merge/push/deploy остаётся
   запрещённым без изменений.
6. **Границы владельца**: merge/push — только OWNER PASS; production — только
   OWNER GO. Автоматического обхода не существует. Staging deploy может
   выполняться оркестратором как проектное действие после успешных тестов
   (контур 5) — без OWNER GO; OWNER GO остаётся обязательным только для
   production.
7. **UX-слой владельца** (PROACTIVE-UX-1, 0.2.0): кнопки следующего шага в
   отчёте (`orch1:<action>:<run_id>`) и детерминированный диспетчер
   `bin/owner_action.sh`. Кнопка = то же явное решение владельца (OWNER
   PASS / OWNER GO), при этом: (а) второй механизм авторизации НЕ вводится —
   используется тот же owner_auth create/consume; (б) исполнение — только
   зарегистрированное project_action точной формы, SHA берётся из
   structured state, не от модели/пользователя; (в) перед каждым действием
   состояние перепроверяется (статус RESULT, SHA ветки против отчётного,
   prior-action, HEAD основной ветки) — устаревшее предложение не
   исполняется; (г) повтор выполненного — нейтральный no-op
   (ALREADY_EXECUTED), не обход и не ошибка; (д) executor слой вызвать не
   может — скрипт вне task-worktree (jail-guard FATAL). Свободный
   merge/push/deploy из executor остаётся запрещённым без изменений.

## Бюджеты выполнения

- turns и календарное время на задачу (профили: fast/balanced/economy);
- **лимит исследования**: чтение без первой записи ограничено (число
  read-вызовов, минуты, компакции истории); после директивы — только запись,
  тест или финальный RESULT;
- **post-write бюджет**: дополнительные turns открываются только после
  первой содержательной записи;
- **финализация**: последние turns — только тест/RESULT (FINALIZE_NOW);
- **reasoning budget**: если ответ исчерпал лимит токенов на внутреннее
  рассуждение (контент пуст) — распознаётся отдельно; один повтор с большим
  лимитом, затем одна эскалация на сильную модель, затем структурный BLOCKED.

## Известные уроки (из реальной эксплуатации)

- read-команды Git не путать с мутирующими (`merge-base` ≠ `merge`;
  `branch --show-current` — чтение);
- регулярное выражение в awk/sed — не файловый путь (`/re/` ≠ `/path`);
- имя файла вида `*.env` с префиксом тоже секрет (`prod.env`);
- модель может потратить весь лимит вывода на рассуждение — нужен детектор;
- длинное слепое ожидание хуже наблюдения за состоянием (`task.sh wait`).

## RESULT-дисциплина

Каждый прогон заканчивается машинно-читаемым RESULT (статусы:
READY_FOR_OWNER_PASS / NO_CHANGE_REQUIRED / NEEDS_OWNER_INPUT / BLOCKED /
FAILED / PERMISSION_VIOLATION) с reason/evidence/tests/writes/commit_sha/
next_action. Заглушек нет: если модель не дала RESULT — раннер собирает его
из фактов. Отчёт владельцу строится всегда и идемпотентно.
