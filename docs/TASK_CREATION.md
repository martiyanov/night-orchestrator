# TASK_CREATION — как Intake формирует постановку для Night Orchestrator

Контракт задачи: `contracts/TASK.schema.json` (проверка — при постановке).
Обязательные поля: `project, task_id, goal, risk, mode, allowed_paths,
forbidden_paths, bootstrap, checks, owner_gates`. Памятка: `checks` — список
**объектов** `{name, command?, timeout_seconds?}` (исполняемые проверки),
не строки.

## Источник полей

| Поле TASK | Откуда берётся |
|---|---|
| `goal` | подтверждённая цель + критерии из intake (`known_facts` + `owner_answers`) |
| `checks` | критерии готовности, которые можно исполнить командой; остальное — в goal |
| `allowed_paths` | подтверждённая область изменений (спрашиваем только если развилка продуктовая) |
| `forbidden_paths` | стандартный набор проекта + явно названные ограничения |
| `risk` | LOW/MEDIUM/HIGH по влиянию (платежи/безопасность/стейт-машина = HIGH) |
| `owner_gates` | решения, остающиеся за владельцем (по умолчанию OWNER PASS) |
| `mode` | read_only для проверки/исследования; writable для изменений |

## Правила

1. В TASK — только подтверждённые владельцем факты; продуктовые гипотезы
   не подставляются молча.
2. Технические детали (файлы, тесты, воспроизведение) исполнитель выясняет
   сам — их НЕ кладём в постановку.
3. Красный тест для бага — требуем в goal («сначала падающий тест»), если
   владелец описал симптом.
4. Один run — одна задача; продолжение после NEEDS_OWNER_INPUT — новый run-id
   и обновлённый TASK.
5. Идентификатор задачи — без привязки к конкретному проекту: любой
   `[A-Za-z0-9_.-]+` (например, TASK-8, INFRA-2, NOTES-1).

## Примеры перехода «сообщение → постановка»

- «Запусти TASK-9» + в бэклоге полная запись → RUN: goal из записи,
  критерии из Done_when, owner gate — OWNER PASS.
- «Хочу улучшить экран сценариев» → вопросы: что именно неудобно? какой
  сценарий считаем правильным? → ответы → TASK или backlog.
- «Проверь, что после релиза всё живо» (без изменений) → RUN, mode=read_only,
  checks: команды-проверки, risk LOW.
