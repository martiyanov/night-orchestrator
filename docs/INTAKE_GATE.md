# Intake Gate — приём задач и цикл уточнений (Night Orchestrator v1.5)

Слой **перед** готовым Orchestrator v1: владелец пишет обычным языком, Intake
понимает намерение, при необходимости задаёт 1–3 вопроса и только потом
формирует TASK (или backlog-запись) и запускает канонический путь. Ядро
оркестратора, safety-гейты, RESULT, отчёты и production-контур не меняются.

## Компоненты

| Часть | Где |
|---|---|
| Движок приёма (детерминированный, без LLM) | `bin/intake.py` |
| Контракт состояния | `contracts/INTAKE_STATE.schema.json` |
| Хранилище состояний | `intake/INTAKE-*.json` (вне репо проекта) |
| Черновики backlog | `intake/backlog-drafts.md` |
| Документация постановки | `docs/TASK_CREATION.md` |

## Типы входящих сообщений (классификация)

| Режим | Смысл | Что делает система |
|---|---|---|
| **DISCUSSION** | обсудить идею, подумать | ничего не запускает и не пишет в бэклог; отвечает по сути |
| **BACKLOG** | сохранить идею/проблему | уточняет (только для качества записи) → черновик записи; НЕ запускает |
| **RUN** | явно «сделай/запусти» | проверяет достаточность постановки → TASK → канонический запуск; иначе вопросы |
| **NEEDS_CLARIFICATION** | промежуточное | 1–3 вопроса владельцу, ожидание ответа, продолжение того же контекста |

Классификация — смысловая, не только ключевые слова: явные маркеры намерения
(«запусти», «сделай», «добавь в бэклог», «обсудим», «отмени») комбинируются с
оценкой полноты постановки (цель? критерий готовности? область изменений?).

## Когда задавать вопросы

Спрашивать — только если неопределённость **меняет результат**:
что именно должно измениться; какой сценарий считается правильным; критерии
готовности; выбор между двумя заметно разными продуктовыми решениями; кому
доступна функция; формат данных/контента; публичный текст; цена/монетизация;
опасное действие; staging/production; важная продуктовая/UX-развилка.

**Не спрашивать** о том, что агент выяснит сам: расположение файлов, какая
функция реализует поведение, какие есть тесты, как создать worktree, какой
рефакторинг меньше, как воспроизвести баг, существующие соглашения проекта.
Такое — задача исполнителя в режиме «только чтение», не владельца.

Формат цикла: **один заход = 1–3 коротких конкретных вопроса**, по возможности
с вариантами ответа. Не переспрашивать известное (TASK, backlog, PROJECT_STATE,
документация, предыдущие ответы в этом же intake-контексте).

## Состояние уточнения

`INTAKE_STATE.json` (одно состояние = один файл `intake/INTAKE-<id>.json`):

```
intake_id, project, original_message, classification,
known_facts[], open_questions[{qid, text, asked}],
owner_answers{qid: text}, proposed_task{}, backlog_draft,
status, chat{chat_id,message_id}, created_at, updated_at
```

Статусы: `NEW → NEEDS_CLARIFICATION → READY_TO_RUN | READY_TO_BACKLOG →
WAITING_OWNER → COMPLETED`; также `CANCELLED`, `DEFERRED` («вернёмся позже»).

## Связывание ответов

Ответ владельца («да», «только Telegram») привязывается к ожидающему intake:
по умолчанию — **единственный** WAITING_OWNER; если таких несколько — система
не угадывает, просит выбрать (название/intake_id). История уточнений не
теряется: ответы дописываются в `owner_answers`/`known_facts` того же файла.

## Backlog

После достаточного уточнения — черновик записи (название; проблема/идея; зачем;
ожидаемое поведение; ограничения; открытые вопросы; критерии, если ясны;
источник/дата). Черновик ложится в `intake/backlog-drafts.md`; перенос в
`state/TODO.md` репозитория — отдельный шаг по обычному процессу проекта
(рабочие копии проекта Intake не пачкает). Перед созданием — поиск похожей
записи в бэклоге проекта: найдено похожее → показать и предложить дополнить,
молча не дублировать.

## TASK для RUN

В TASK попадают **только подтверждённые факты**: цель, критерии готовности
(объекты-проверки), допустимые области изменений, ограничения, риск,
owner gates. Продуктовые решения, которые владелец не подтверждал, — не
придумываются. Технические детали, которые исполнитель выяснит сам, — не
нагружаются в постановку.

## Запуск

`READY_TO_RUN` → новый уникальный run-id (`дата-слаг-NN`) →
`task.sh new` + `night_run.sh` (канонический путь, никаких обходов).
Дальше работает существующий Orchestrator v1. Intake сам ничего не
реализует, не деплоит и не обходит OWNER PASS/OWNER GO.

## NEEDS_OWNER_INPUT из оркестратора

`intake.py from-result <run_dir>` превращает RESULT в понятный вопрос
владельцу (тот же цикл). После ответа: факты дополняются, предлагается
продолжение **с новым run-id** (завершённые run-id не переиспользуются).
Если ответ меняет требования настолько, что постановка иная — сначала
обновление TASK (владелец видит и подтверждает), не автозапуск.

## Отмена и откладывание

«отмени» / «пока не делай» → CANCELLED; «положи в бэклог» → переход в
BACKLOG-ветку; «вернёмся позже» → DEFERRED. Выполнение не стартует, история
не удаляется.

## Кнопки

Приоритет — надёжный текстовый цикл. Кнопки Intake-уровня ([▶ Выполнить]
[📝 В бэклог] [✖ Отменить]) и OWNER PASS/merge/deploy через кнопки — не
связаны и по умолчанию выключены (безопасность важнее интерфейса).

## Общность

Ничего проектно-специфичного не зашито: проект — из реестра
`config/projects.json`; пути — от `ORCH_ROOT`; Telegram chat_id и модели
движку неизвестны (доставка ответов — за вызывающим). Слой переносим в
отдельный репозиторий вместе с оркестратором.

## Архитектурная граница (важно)

Intake — **вызываемый модуль, а не глобальный перехватчик**. Он НЕ встроен в
OpenClaw и не классифицирует все входящие сообщения хоста: OpenClaw здесь —
личный ассистент с несколькими проектами, Night Orchestrator — универсальный
исполнительный механизм. Целевая цепочка для проекта (шаблон: examples/skills/example-project):

```
OpenClaw main assistant → навык проекта (project skill)
  → bin/intake.py (классификация/уточнения/TASK)
  → Night Orchestrator (исполнение)
```

- **Универсально** (без привязки к проекту): классификация намерений, правила
  вопросов, состояние INTAKE_STATE, связывание ответов, дедупликация бэклога,
  формирование TASK (профиль проекта — из `config/projects.json`: bootstrap,
  forbidden_paths, репозиторий), запуск, from-result, отмена/откладывание.
- **Проектно-специфично** (живёт в реестре/навыке проекта): имя проекта по
  умолчанию (`INTAKE_PROJECT`), список bootstrap-документов, forbidden_paths,
  где искать бэклог для дедупликации.
- Навык проекта вызывает `intake.py` со своими параметрами (`--project`,
  `INTAKE_DIR` может быть у каждого проекта свой) и доставляет вопросы/отчёты
  владельцу в свой чат.

## Интеграция с OpenClaw: проектные навыки

```
OpenClaw main assistant
├── обычная работа ассистента (личные запросы — Intake НЕ вызывается)
├── проектный навык  (<workspace>/skills/<project>/)
│   └── bin/intake.py --project <project-id>
│       └── Night Orchestrator v1
├── (будущее) навык MindSpace — та же схема, свой --project
└── другие навыки
```

- **Граница навык/оркестратор**: навык — тонкий маршрутизатор (распознал
  обращение → вызвал Intake → переслал вопросы/статусы владельцу); Intake —
  проектно-нейтральная логика приёма; оркестратор — исполнение. Навык не
  реализует код, не вызывает run_task.sh, не делает merge/deploy.
- **Почему Intake не глобальный перехватчик**: активация только явным
  обращением («Агон:», «/agon») или уже установленным проектным контекстом;
  похожее-но-неявное → вопрос-подтверждение, ничего не запускается; личные
  сообщения навык не трогает (детерминированный route.py).
- **Выбор проекта**: префикс навыка; project_id — в project.json навыка, из
  реестра берётся профиль (репозиторий, bootstrap, запреты).
- **Связывание ответов**: состояние ожидания живёт в Intake (WAITING_OWNER);
  навык передаёт ответ как есть (`intake.py answer`); несколько ожидающих —
  Intake просит выбрать, навык переспрашивает владельца, не угадывает.
